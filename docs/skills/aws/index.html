Image Forge

Built

  • I own the platform's machine image (AMI) and container image release systems: the Packer builds, the release metadata, sharing released images with the other AWS accounts, and runtime support. I built the layered model on this page, which shipped in mid-2025.

    Read in context
    1. Metadata. Each application declares its runtime, version and CPU architecture. The platform supports several Java, Tomcat and Node versions on two Amazon Linux releases, for both x86 and ARM (Graviton), and keeps the two previous versions alongside the current one.
    2. One pipeline. The pipeline reads the metadata and builds the image layers the application asks for.
    3. Two kinds of build. Snapshot builds skip the application bake, so feedback comes back fast while a team is developing. They are never promoted. Release builds do the full bake and run Python (pytest) tests inside the image.
    4. Promotion gate. A release is promoted only with a green bake and a clean security scan, or an approved exception.
    5. Shared across accounts. The release is shared with the AWS accounts that use it, and tags record its lineage. Releases move from snapshot to release to stable to deprecated. Stable keeps the previous version for rollback, and pulled images are quarantined.
    6. Reaching applications. Containers pick up new releases through moving release tags and an automated patching operator, in monthly patch groups. EC2 applications are rebaked and rolled by a shared patch pipeline.

  • Teams can choose their runtime version and run on ARM (Graviton) instances, which the old model didn't support.

Safe Deploys

Co-developed with my team

    1. Build. The shared build stage produces the release.
    2. Start the new copy. The release starts as a new copy of the service (green) beside the live one (blue). No live traffic goes to it.
    3. Health gate. Green has to pass health checks before any live traffic reaches it. If it fails, the rollout stops there, and live traffic never moved.
    4. Approval. A person approves each traffic step.
    5. Shift traffic. The Application Load Balancer moves a share of traffic to green. Steps 4 and 5 repeat until all traffic is on green.
    6. Done. With every step approved, green becomes the live version.
    Read in context

  • Tools: Harness runs the pipeline, Application Load Balancers shift the traffic, and the services run on EC2 or Amazon EKS.

Kube Fleet

Built and operates

  • I build and run the company's Kubernetes platform with my team: a Fargate-only EKS estate spread across many AWS accounts.

    Read in context

  • I build and run the EKS estate with my platform team. Each cluster runs the same platform extensions: the AWS Load Balancer Controller, cert-manager, external-dns, Fluent Bit, kube-prometheus with Thanos and Grafana, a cost exporter and in-house operators.

    Read in context
    1. Define. Reusable Terraform modules define a cluster and its platform extensions.
    2. One run. A single Terraform run creates the cluster, the same way every time.
    3. Run on Fargate. Every workload runs on Fargate, so there are no worker nodes to manage.
    4. Platform extensions. Each cluster gets the same set: traffic (the AWS Load Balancer Controller, cert-manager, external-dns), logs (Fluent Bit) and metrics (Prometheus, with Thanos and Grafana, and Alertmanager for alerts).
    5. Monthly patching. Containers pick up patched base images every month through moving release tags and an automated patching operator. That flow is on the runtime images page.

  • Container registries and other container resources are separate: they ship on every merge to the infrastructure repository.
