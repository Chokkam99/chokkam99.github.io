Safe Deploys

Co-developed with my team

A shared deployment path for EC2 and EKS services. Each release starts as a new copy beside the live one and must pass health checks before it takes any live traffic. Traffic then moves over in approved steps, and a person can roll back at any step.

About me

The problem

The company's standard delivery platform runs hundreds of production deployments a day, for teams across the company.

At that volume, some releases will be bad. A service won't start, or it can't reach something it depends on. The deployment path has to expect that and make the safe outcome the default, so a bad release fails in the pipeline instead of in front of customers.

My part

This is a team system. A sibling platform team created the company's standard delivery pipeline.

On that pipeline, I built the shared build stage and the delivery paths for AWS Lambda and AWS Bedrock AgentCore. The AgentCore path has its own page.

I co-developed the EC2 and EKS paths on this page with the rest of my platform team: the health gating, approvals, traffic shifting and rollback. I was one of several engineers on them.

I also wrote the Open Policy Agent policies in Harness that moved non-compliant pipelines on the standard path from warnings to hard blocks, as the legacy pipelines are retired.

How it works

  1. Build. The shared build stage produces the release.
  2. Start the new copy. The release starts as a new copy of the service (green) beside the live one (blue). No live traffic goes to it.
  3. Health gate. Green has to pass health checks before any live traffic reaches it. If it fails, the rollout stops there, and live traffic never moved.
  4. Approval. A person approves each traffic step.
  5. Shift traffic. The Application Load Balancer moves a share of traffic to green. Steps 4 and 5 repeat until all traffic is on green.
  6. Done. With every step approved, green becomes the live version.

A rollback starts when a person rejects a traffic step or asks for one. Traffic then returns to the last healthy version, and the rollback is built to finish without manual work.

Tools: Harness runs the pipeline, Application Load Balancers shift the traffic, and the services run on EC2 or Amazon EKS.

The key decision

The main design choice is where automation stops. Health checks before traffic are automatic. Moving to the next traffic step, or rolling back, is a person's decision, and once someone decides to roll back, the rollback runs on its own. Nothing promotes a release automatically from live metrics, which is why I call this a progressive rollout with approval gates rather than a canary.

The reasoning: checks that run before traffic catch the failures that are cheap to detect, like a release that won't start or fails its health endpoint, and they cost customers nothing. Automated promotion needs trustworthy signals for each service and enough traffic to judge them. Across many teams running very different services, those signals vary a lot, so a person who knows the service, watching its own dashboards, is the simpler gate for each step.

Starting a full new copy instead of replacing the live one in place has a cost: two copies run during a rollout. In return, the live version is untouched until the new one has shown it can run, and going back is a routing change rather than a redeploy.

Outcome

Most production deployments run through the standard path. The rest run on separate legacy pipelines that are being retired.

Go deeper

Health signals

On EC2, the gate waits for the new instances to report healthy. On EKS, it waits for the new pods to reach a steady state. Both happen before the load balancer sends green any live traffic.

One rollout at a time

Only one rollout runs per service and environment at a time. A deployment lock enforces it, so two pipeline runs can't fight over the same load balancer.

A failure case I use to test designs

Suppose a pipeline times out right after asking the load balancer to shift traffic. Its own record says the shift was requested, but nobody knows whether it was applied. Reversing the step blindly can make things worse. The safer recovery reads the load balancer's actual state, decides which version should be live, moves routing to match, and only then lets the next rollout start. My rule of thumb for any deployment system: trust the observed state over the pipeline's memory of what it asked for.

What I would add next

For services with steady traffic, I would add automated analysis of error rates and latency between steps, as a second signal next to the human approval. For low-traffic services I would keep the human gate on its own, because there isn't enough traffic to judge automatically.
