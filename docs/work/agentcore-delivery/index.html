About me

The problem

AgentCore was new: we had early access to it with AWS, before it was generally available.

A few SDK calls and a script can deploy an agent for a demo, but a production agent needs what any production service gets: a repeatable build, testing before it takes real traffic, a controlled promotion, and the same access and security rules as everything else. Without one shared path, every team would work all of that out alone, on a service that was still changing under them.

My part

I took the deployment path from design, while AgentCore was still in preview with AWS, to production. I built the CDK stacks for AgentCore Runtime and Gateway, onboarding through the self-service platform, the image bake, staged validation, gated promotion, and the check that the live version is the one we shipped.

I also wrote the AgentCore log forwarding and set the platform's IAM role naming convention for AgentCore Gateway.

Another team builds the agent template that teams start from. I drove its platform requirements.

To get teams started, I led eight two-hour, hands-on sessions, one for each business domain, on what the platform is and how to onboard an agent. The platform sections were mine; the template team presented its own.

I own the infrastructure and the delivery path. The agents themselves, and their code, belong to the teams that build them.

How it works

  1. Onboard. A team registers its agent through the self-service platform.
  2. Provision. CDK stacks create the AgentCore Runtime and Gateway.
  3. Build. The standard pipeline bakes the agent's image.
  4. Validate in stages. The new version runs on a staging endpoint and is tested there first.
  5. Promote. A gate promotes the tested version to production.
  6. Verify. The pipeline confirms the live endpoint is serving the new version.

The key decision

The main choice was to treat an agent like any other production service: one productized path, defined as code, that every agent ships through, instead of per-team scripts.

The service was new and still changing. With one path, the platform absorbs each change once instead of every team chasing it, and security and operations have one place to look.

Outcome

Every production AgentCore agent at the company ships through this path. None uses the old SDK and script route.

Several teams run agents in production on it, many with more than one.

Go deeper

What AWS runs and what the platform adds

AgentCore itself runs each session in its own isolated micro-VM and provides versioned endpoints. On top of that, the platform sets up a least-privilege model with three separate identities (the user, the agent's own role, and the identity it uses to call other systems), guardrails at the organization and application level, a three-tier evaluation setup, OpenTelemetry instrumentation, and the staged test-and-promote flow above.
