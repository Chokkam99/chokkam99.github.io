About me

The problem

Every new service needs the same groundwork: somewhere for its code, somewhere for its container images, a place to run, and a pipeline to deploy it. If each piece is a separate request to the platform team, every new service starts with a wait, and every team sets it up a little differently. With many teams shipping services, that groundwork has to be self-service and come out right by default.

My part

I built the platform end to end.

Much of the newer self-service infrastructure is built from reusable AWS CDK constructs and stacks. I wrote constructs for Application Load Balancers, a web application firewall that blocks by default, Lambda authorizers, Network Load Balancers and container registries. I also built the self-service workflow teams use to create Application Load Balancers, and I'm extending it to listener rules and target groups.

When a team arrives with a new design, I often represent the platform. I lead the session, map their stack to the patterns the platform supports, work out what it needs for infrastructure, security, networking, observability, identity and deployment, split the work between teams, write the platform stories, and follow through until it runs in production on a supported setup.

On the delivery side, I wrote the policy-as-code rules that block non-compliant pipelines. That part is on the deployments page.

How it works

  1. Request. A team picks what it needs from a self-service catalog.
  2. One workflow. It creates the whole set together: the code repository, the container registry, the Kubernetes namespace and the deployment pipeline.
  3. Ship. The new service deploys through the company's standard delivery pipeline.
  4. More of the same. The catalog offers other infrastructure, such as Application Load Balancers, self-served the same way.

The key decision

The main choice was to create everything a new service needs in one workflow.

The four pieces only work together: the pipeline needs the registry, and the deployment needs the namespace. Creating them in one pass means names, permissions and settings line up from the start, and nobody has to stitch them together by hand or file one request after another.

Outcome

The platform covers a broad catalog of infrastructure and is used by many teams across the company, without routine manual work from the platform team.

Go deeper

The API Gateway platform

I primarily drove a spec-driven, self-service platform for API Gateway that replaced a process built on Jenkins, custom CDK and manual deploys. To wire integrations into a team's API spec, I explored five approaches in my own branches; the one we chose shipped as the self-service platform's integration-wiring page.

I built parts of the stack and construct code: loading specs from S3, VPC Link wiring, VPC endpoint and hosted-zone discovery, mutual TLS, the HTTP integration mode, an OpenAPI-only mode and base path mappings. I also ran the migration from the old process: the field mapping, the changes that would break a deploy, and walking the first team through it.

A defect in the old process

While researching the old process, I found why API stages kept falling out of CloudFormation's tracking: each deploy generated only the stage it targeted, with a retain policy, so every other stage was dropped from the stack. I confirmed the new design avoids it, worked through the relevant CloudFormation limits (resource counts, template size, stage ceilings), and scoped the follow-up work.

One design, end to end

A team arrived with a multi-tier AWS application. I turned their design into platform requirements and helped take an optional web application firewall for load balancers from a security draft to a supported option on the existing platform stack. I shaped and sequenced the stories, agreed the production blocking posture with the security team, reviewed the construct and stack changes, and supported that team as the first to run it in production. I didn't design their application.
